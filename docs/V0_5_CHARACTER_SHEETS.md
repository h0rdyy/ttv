# TTV v0.5 — Universal Character Sheets

## Цель

Убрать игровые характеристики из platform core и дать мастеру простой способ собрать лист персонажа под свою систему без изменения кода TTV.

## Архитектура

Шаблон листа и значения персонажа разделены:

```text
ActorSheetTemplate
  └─ schema: секции + поля

Actor
  ├─ sheet_template_id
  └─ system_data: конкретные значения этого персонажа
```

Один шаблон может использоваться многими героями/NPC. Изменение структуры шаблона не копирует схему в каждого Actor.

## Типы полей MVP

- `text` — текст;
- `number` — число;
- `checkbox` — флажок;
- `resource` — пара `current / max`.

Шаблон состоит из разделов, разделы — из полей. Поля имеют внутренний key, отображаемое название и необязательную подсказку.

## Права

- Owner / GM / Assistant GM создают, редактируют, удаляют и назначают шаблоны;
- GM-роли могут редактировать лист любого доступного Actor;
- Player может менять только `system_data` назначенного ему Actor;
- Player не может менять чужого Actor или структуру шаблонов;
- участники кампании могут читать нужные им шаблоны через RLS.

## Совместимость

Новые Actor больше не получают из ядра жёсткие `hp / armor / level`. Если в кампании есть основной шаблон, он автоматически назначается новому Actor, а `system_data` начинается с `{}`.

Существующие Actor не мигрируются насильно: старые значения `system_data` сохраняются. Legacy HP в текущем combat/sidebar остаётся для обратной совместимости до v0.6, где ресурсы и бой будут обобщены.

## UI

На online-столе появился компактный слой листов поверх стабильного v0.4 стола:

- GM: выбор Actor → `◇ Лист`;
- GM: `⚒ Листы` → управление шаблонами и назначением;
- Player: `◇ Мой лист`;
- `Esc` закрывает открытый лист/менеджер.

Конструктор шаблона позволяет добавлять/удалять разделы и поля, выбирать тип поля и подсказку, а также отметить шаблон как основной для новых персонажей.

## Automated acceptance

Перед merge v0.5 должны проходить:

```bash
npm ci
npm audit --omit=dev --audit-level=high
npm run typecheck
npm run build
```

DB sanity:

1. GM создаёт основной шаблон.
2. Новый Actor получает этот `sheet_template_id` и пустой `system_data`.
3. Player обновляет лист своего назначенного Actor.
4. Player не может обновить чужого Actor.
5. Player не может создавать/редактировать шаблоны.
6. Старые сцены, токены, инвентари, fog и карты сохраняют целостность.

## Первый полноценный плейтест после v0.5

Нужны минимум два браузерных сеанса и два аккаунта: GM и Player. Желательно провести короткую 30–60-минутную сцену, а не просто нажимать кнопки.

1. GM открывает существующую кампанию и создаёт шаблон `Плейтест`.
2. Создаёт 3 раздела: `Основное`, `Ресурсы`, `Навыки`.
3. Добавляет все четыре типа полей, например:
   - Имя концепта — текст;
   - Сила — число;
   - Ранен — флажок;
   - Выносливость — ресурс current/max.
4. Делает шаблон основным и создаёт нового героя/NPC. Проверяет, что шаблон назначился автоматически и нет автоматически придуманных TTV характеристик.
5. Назначает героя Player-аккаунту.
6. Player открывает `Мой лист`, меняет значения и сохраняет. GM после realtime/server refresh видит новые значения.
7. GM открывает лист того же героя и меняет одно значение; Player получает обновление после синхронизации.
8. GM создаёт второй шаблон с другой структурой и назначает его NPC — две разные формы должны спокойно жить в одной кампании.
9. Проверить обычный игровой цикл: смена сцены, кастомная карта, zoom/pan, live drag токена, fog, выдача предмета, инвентарь, заметка и короткий бой.
10. Обновить обе страницы. Шаблоны, назначения, значения листов, карта, fog, токены и предметы должны сохраниться.
11. Player не должен видеть кнопки управления шаблонами и не должен иметь способ изменить чужого персонажа.
12. Все найденные неудобства делим на `blocking`, `annoying`, `polish`; во время плейтеста не добавляем новые крупные фичи, пока не соберём список.

## Что намеренно не входит в v0.5

- формулы и вычисляемые поля;
- автоматические модификаторы;
- броски из поля листа;
- conditions/effects;
- tabs внутри листа;
- drag-and-drop layout builder;
- dynamic visibility отдельных полей;
- импорт готовых коммерческих игровых систем.

Это относится к следующим milestones. v0.5 должен доказать, что TTV может хранить и показывать разные листы без привязки ядра к конкретной RPG.

Следующий milestone после плейтеста: **v0.6 — Combat / Dice / Effects**.
